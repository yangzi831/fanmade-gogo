# fanMade GoGo!

**Made by fans. Shared with fans.**

面向音乐节、剧场、演唱会等活动的粉丝自制物料分享、领取和互换网站。分享贴纸、明信片、徽章、应援牌，也可以发布未关联活动的日常物料。

**[访问网站 → fanmade-gogo-share.netlify.app](https://fanmade-gogo-share.netlify.app/)** · [提交问题或建议](https://github.com/yangzi831/fanmade-gogo/issues) · [配置与部署](docs/SUPABASE_SETUP.md)

> 当前状态：已公开部署，处于早期多人试用阶段。下方进度核对日期为 **2026-10-20**。核心领取、互换和库存流程已接通；最新完整需求仍在分阶段实现，暂不视为全部完成。

## 这是什么

制作人可以把自制物料发布到稳定的公开主页，或加入全站共享活动，让同场观众找到自己的作品。领取者无需登录即可浏览，同一发布者、同一活动的多件物料可以一次申请，之后凭专属链接或账号记录查看交接状态。

每个人使用同一种账号，既能发布，也能领取和互换。没有开店或身份切换流程；预约、交接和库存由真实后台统一处理。

- **活动全站共享**：同一场活动可以有多位制作人，分别拥有和管理自己的物料。
- **库存独立管理**：收藏和分享只引用原物料，不复制库存；不同活动的实物份数需要明确分配。
- **浏览公开，申请私密**：公开页面不返回联系方式、私密备注或预约列表。
- **手机、平板和电脑共用**：移动端卡片浏览与现场核对，桌面端多列清单、管理侧栏及编辑预览。

## 从这里开始试用

1. 打开 [线上网站](https://fanmade-gogo-share.netlify.app/)，在“发现”中切换物料、活动和制作人，或搜索已有内容。
2. 注册自己的账号，进入“我的 → 管理我的物料”，或直接点击“发布物料”。
3. 发布时搜索并加入已有活动；没有合适记录时，核对相似活动后添加，也可不关联活动。
4. 上传物料图，填写说明、数量和领取方式；支持连续添加、保存草稿、预览后发布。
5. 将公开主页或物料清单链接分享给其他人。申请成功后，在“记录”或管理区处理交接。

线上使用真实共享数据库，操作会保存。请自行注册测试账号；下文公开密码的演示账号仅用于本地演示库，不能当作线上管理员凭据。云端已有的验收账号、活动和物料可能带有“测试”或“公网验收”标记。

### 当前规则：哪些已经生效

- 可预约量 = 总量 − 已预留 − 已送出。后台事务校验整份申请，任一物料不足就整单失败；多个用户争最后一份不能超额预留。
- **普通领取提交即预留，直接进入待领取**；最新规划中的“已预留但待发布者确认”尚未实现。
- **互换提交时不预留**；发布者接受时再次检查余量，成功才进入待交换。取消／拒绝释放已经预留的部分，完成时将预留转为已送出，重复操作不会再次扣减。
- 现场手动登记只使用未预留库存；已有线上预约应从对应记录完成交接，避免重复登记。
- 调整总量不能低于已预留与已送出之和。不同活动各分配独立库存，不自动将同一份实物复制到多场活动。
- 暂停和预约截止都会阻止新申请，已有预约保留；不自动超时释放。
- **当前限领仍按同一活动、同一物料、规范化联系方式累计**，包含待确认互换；最新要求的“每次预约限领”尚待修改。免登录不能严格识别同一个人，不宣称能完全防重复领取。
- 领取码用于现场搜索核对；私密记录还需要双方账号或不可猜测的专属查询凭证。请勿将私密查询链接当公开分享链接。
- 记录图片名称目前跟随物料当前版本，历史快照及软删除尚未完成。状态通过刷新查询同步，尚无实时推送或通知发送。
- 分享引用原库存；图片内数量是生成时快照，打开网页后查询当前数量。公开列表允许短时缓存，提交预约始终重新校验库存。

规则实现主要集中在 `server/rules.mjs`、`server/materials.mjs`、`server/availability.mjs`；更多背景见 [RULES.md](docs/RULES.md) 和 [SHARED_EVENTS.md](docs/SHARED_EVENTS.md)。部分早期文档中的“仅本地／SQLite／未部署”描述属于当时阶段，当前线上架构如下。

## 技术与持久化

| 层级 | 当前线上方案 | 本地独立演示方案 |
| --- | --- | --- |
| 前端 | React 19 + TypeScript + Vite，Netlify 静态资源 | 同一套前端，Vite 开发或 Express 提供构建产物 |
| 业务 API | Express 5 + Netlify Functions | 常驻 Node.js + Express |
| 账号 | 自有用户名／密码、bcrypt 哈希、HttpOnly Cookie 会话 | 同一认证逻辑 |
| 业务数据库 | Supabase PostgreSQL，Singapore | SQLite WAL，`data/materials.sqlite` |
| 图片 | Supabase 私有 Storage，经后端检查公开性／双方权限后返回 | `data/uploads/` 本地磁盘 |

**当前未接入 Supabase Auth**：网站账号保存在业务 schema `fanmade.users`，不会显示在 Supabase Authentication → Users 中。RLS 已启用，业务表不直接向 anon／authenticated 开放；服务端仍必须检查每项操作的归属。

GitHub 仅保存源码，不保存业务数据库或用户图片。浏览器 sessionStorage 仅保存未提交清单及请求幂等键，不能替代多人共享后台。本地 SQLite 和线上 Supabase 是两套数据，不会自动同步；迁移旧数据需要另做备份、导入及库存核对。

图片在浏览器上传前压缩，后台用 Sharp 转为 WebP，并生成最大 480px 的缩略图；原图最大边长 1600px，不强行裁切作品。私密备注图不开放匿名访问。Netlify Function 已配置图片二进制响应，缩略图链接带版本号以避开旧的损坏缓存。

## 本地运行

需要 **Node.js 22.10 或更高的 22.x 版本**与 npm，推荐使用最新维护的 22.x。SQLite 使用 Node 内置实验性接口，启动脚本已包含对应参数。

### 独立本地演示库

```powershell
npm ci
npm run seed
npm run build
npm start
```

打开 **http://localhost:3001/**。开发模式运行 `npm run dev`，前端地址为 **http://localhost:5173/**，接口代理到 3001。通常无需配置 `.env`，自定义端口和来源时参考 [.env.example](.env.example)。

| 贴纸盒 | `wuwei` | `Demo2026!share` | `/u/wuwei` |
| 徽章夹 | `xiaoyu` | `Demo2026!share` | `/u/xiaoyu` |

全新演示库包含两位制作人、三场示例活动及七件物料，另收录 CAN 活动和海报。演示数据有明确标记，操作真实保存。`seed` 检测到演示账号后会跳过，不用于重置或替换数据；正式环境不要执行 seed，不要使用公开演示密码。已有本地库无需重复初始化。

### 本机连接 Supabase

```powershell
npm ci
Copy-Item .env.cloud.example .env.cloud
# 用编辑器填写本地 .env.cloud，已有文件时不要覆盖
npm run build
npm run cloud:check
npm run cloud:init
npm run cloud:start
```

打开 **http://localhost:3003/**。该模式仅绑定本机，但账号、申请、库存和图片写入真实 Supabase。已有 `.env.cloud` 时跳过复制步骤。

字段来源、SQL、私有桶和初始化步骤见 [SUPABASE_SETUP.md](docs/SUPABASE_SETUP.md)。管理员通过本地 `OWNER_*` 初始化配置创建；再次初始化不会覆盖现有账号或密码。不要把管理员密码复制到 README 或线上运行环境。

## 部署与数据保护

当前公开地址为 **https://fanmade-gogo-share.netlify.app/**，由 GitHub `main` 分支触发 Netlify 构建；网站、函数路由及构建命令在 [netlify.toml](netlify.toml)。

部署自己的实例时：

1. 创建 Supabase 项目，按配置文档填写本地文件并执行 `cloud:check`、`cloud:init`，初始化业务表、私有图片桶与管理员。
2. 将仓库导入 Netlify，使用 `npm run build` 构建、`dist` 发布目录及已有 Functions 配置。
3. 在 Netlify 环境变量中配置 `DATABASE_URL`、`SUPABASE_URL`、`SUPABASE_SECRET_KEY`、`SUPABASE_BUCKET`、`APP_ORIGIN`、`NODE_ENV`、`TRUST_PROXY`；`APP_ORIGIN` 是最终 HTTPS 来源且不带末尾斜线。本机代理 `DATABASE_PROXY_URL` 不应复制到线上。
4. 部署后以两个独立账号完成发布、申请、处理和库存核对，并测试匿名浏览及第三方越权拒绝。

`.env`、`.env.cloud`、`.env.production`、`.netlify/`、`data/`、`output/` 均被 Git 忽略；仅空配置模板允许提交。数据库连接串和服务端 Secret key 只给后台使用，不使用 `VITE_*` 暴露到浏览器，不提交到 GitHub。

当前采用免费方案试用，不承诺免费套餐下的生产可用性。Netlify 和 Supabase 有独立额度，冷启动、项目闲置暂停、用量限制和跨境网络会影响体验；使用前以各自控制台及官方当期规则为准。免费方案比较见 [FREE_HOSTING.md](docs/FREE_HOSTING.md)，它是历史评估，不能替代最新计费规则。数据库与图片需要分别备份；只保存 Git 仓库不能恢复用户数据。

如需自托管，可参考 [DEPLOYMENT.md](docs/DEPLOYMENT.md) 的 Docker／VPS + SQLite 持久化方案；它是另一种部署方式，不是当前 Netlify 站点的运行架构。

## 测试与多人验证

```powershell
npm test
npm run build
```

截至最近一次代码交付（2026-10-15），**34 组自动化测试与生产构建通过**，覆盖所有权与私密图片、批量草稿发布、活动共享、取消／完成、幂等重试、跨进程最后一份争抢、现场登记及分享范围。测试包含 SQLite 多进程和 PostgreSQL 兼容引擎；真实 Supabase 的单独验证记录见 [CLOUD_VERIFICATION.md](docs/CLOUD_VERIFICATION.md)。该文档记录初次接入，之后已完成 Netlify 公网部署、双账号交接验收及线上图片解码修复。

手动多人验证可使用两个浏览器或普通／隐私窗口，连接**同一个后端地址**：

1. A 发布物料；B 用另一账号打开 A 的公开主页，在同一活动内选择多件申请。
2. A 在“管理 → 收到的申请”查码；B 在“记录 → 我领取的”查看同一交接状态。
3. A 完成交接，两边刷新，确认预留转为已送出；重复完成不再次扣量。
4. 另建可取消申请验证库存释放；互换先提交不占库存，接受后才占用。
5. B 不能修改 A 的物料；第三个账号或匿名窗口不能读取双方私密记录、联系方式和备注图片。

`npm run cloud:verify` 会对配置的真实 Supabase 写入带测试标记的数据，注册测试账号并验证库存；请明确选好环境后执行。私密测试凭据和结果保存在忽略提交的 `output/`，不要公开上传。

桌面／手机视口检查及二维码自动解码已有记录，但不能代替微信实机验收。iOS／Android 图片保存、微信长按识别、现场弱网、真实多用户负载仍需持续测试。
