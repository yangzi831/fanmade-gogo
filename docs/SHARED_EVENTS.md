# 共享活动：当前实现与默认规则

## 数据来源和数据关系

原首页卡片已由 SQLite 的 `events` 记录生成，初始三个入口是 `seed` 写入的演示活动。这次保留卡片与活动入口，将原来“一位制作人拥有一场活动”调整为：

- `events`：全站共享的演出名称、城市、日期、场次、场地、结束日期/时间和主题。
- `event_creators`：制作人加入活动的关系，各自的领取说明与清单公开开关。
- `materials.creator_id`：物料归属，不再从活动创建人推断权限。
- `reservations.creator_id`：每份预约归属；互换申请仍独立存储，继承预约归属。
- `events.owner_id`：仅保留最初记录创建者的历史信息，不授予其对其他制作人物料的权限。

共享活动页 `/e/:id` 汇总公开且有物料的制作人；独立清单 `/e/:id/by/:username` 仅显示对应制作人的作品、库存和说明。个人主页的活动卡片直接进入独立清单。预约结果和查询页注明制作人。

## 从添加到自动出现入口

1. 站点管理员登录工作台，打开“管理全站活动库”，搜索后添加。只录入活动，不自动加入，也不会凭空出现在首页。
2. 制作人点击“选择活动发布物料”，按名称、城市、日期、场次、场地搜索。多个关键词用空格组合匹配。
3. 选择活动后幂等地创建加入关系，自动选中该场并打开物料发布表单。新加入的清单默认公开；尚无物料时不计入首页。
4. 保存第一件物料后，下次打开或刷新首页，该场活动会自动展示。已有其他制作人时仍只有一个活动入口，数量自动汇总。
5. 访客从首页搜索能找到尚无公开物料的活动。“发布第一份物料”会先登录/注册，再返回所选活动，自动加入并打开表单。
6. 搜索未找到时，普通制作人也可添加新活动。提交前显示可能重复的记录，选择已有记录即可继续加入与发布。

仅隐藏自己的清单会隐藏自己的所有物料，并停止新预约；其他制作人的作品、库存和预约不受影响。已有预约仍能查询、取消和在后台处理。所有读取与修改权限在服务端检查；加入同场不会获得其他制作人的预约、联系人或图片权限，站点管理员也不例外。

## 活动识别与重复处理

完全相同活动的身份由 **名称 + 城市 + 活动日期 + 场次 + 场地** 五项组合决定。先做 NFKC、去空白和大小写规范化，数据库唯一索引与写事务确保两进程并发创建也只成功一次。主题和结束时间不影响活动身份。

可能重复的候选规则：名称相同或相互包含，且同城或日期相差不超过 7 天；或者同城、同场地、同一天。候选中完全相同的记录禁止再次创建；仅相似时须显式勾选“我已核对，这是一场不同的活动”。名称相同而城市、日期、场次、场地不同可以是不同记录，不能仅按名称合并。

这只是初步辅助：不自动识别别称、错别字、简繁体或“上海/上海市”等同义地名。暂不自动合并疑似重复活动；管理员核对后编辑共享元数据，冲突仍会再次校验。没有活动删除或在线合并工具。

## 首页、搜索与时间

- 首页默认：活动公开、至少一件来自公开制作人清单的物料、尚未结束；按日期/场次/名称排序。
- 数量按公开清单中的物料记录计算。库存为零的作品仍算公开物料，仍可浏览与提出互换。
- 搜索包含空活动、清单全部隐藏的活动与已结束活动；展示制作人数、物料数和结束标识，城市与日期可单独过滤。
- 日期过滤包含活动起止日期之间的任一天。默认场次为“全天”；结束日期默认活动当天，结束时间默认 23:59，按北京时间 `Asia/Shanghai` 判断。
- 结束仅影响默认首页展示，不自动关闭预约、不释放库存。没有后台推送；导航或刷新后读取最新数据库结果。

## 权限与预约

共享元数据由站点管理员后续编辑；普通制作人可添加缺少的活动，并只维护自己的清单设置、物料和预约。当前库迁移时最早注册账号成为管理员，本地演示为 `wuwei`；空库首次注册者成为管理员。不新增其他管理员、审核或活动认领流程。

一份预约必须属于同一场活动的同一位制作人。多位制作人的作品需要分别预约，生成各自领取码和查询链接；跨制作人拼单在后台整体拒绝，库存不变。原有事务、限领、免费预留、互换确认、取消释放与幂等核销规则不变。

## 旧数据迁移

启动时以 `PRAGMA user_version=1` 自动迁移。非空旧库会先通过 `VACUUM INTO` 保存一致性快照 `data/before-shared-events-时间戳.sqlite`，然后事务迁移。原活动变成共享记录，旧领取说明和公开状态移入该制作人的加入关系，物料和预约回填原制作人。

旧地点按 `·` 拆城市/场地；无法识别城市时填“待补充”。旧数据没有场次，填“全天”。请管理员逐条补充正式演出名称、城市和实际场次。旧库五项完全相同时合并为一场并保留别名映射；仅相似记录不合并。

原 `/e/:id` 仍能打开对应活动（现在为汇总页）；合并后的旧 ID 自动解析到保留记录。已保存的旧预约查询链接不变，原库存、领取码、会话和密码哈希保留。旧结算路径会尝试根据未提交选择恢复到对应制作人的清单；无法判定时返回活动汇总页。

当前本地实际迁移核对：3 场活动、7 件物料、2 份已有预约，数量和活动 ID 均保留。测试新增内容使用临时数据库，不写入现有本地库。

## 后续需求待确认

1. 活动名称、城市、场地和场次是否使用受控字典，是否支持别名、演出系列与多场次关联？
2. 制作人新增活动是否需要审核？共享活动是否需要举报重复与管理员在线合并？
3. 活动结束后是否同时停止新预约？是否存在独立预约截止时间？
4. 当前不同制作人分别预约是否长期保留，是否需要跨制作人统一凭证？
5. 是否需要管理多个站点管理员，以及活动资料变更历史？

部署仍为原 Express + 持久化 SQLite/上传目录，无需新增云服务。部署已有数据前应备份数据库与上传目录，使用单个迁移实例首次启动，确认迁移成功后再启动其他进程。
